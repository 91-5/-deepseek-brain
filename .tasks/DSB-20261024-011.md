## Context

`deepseek-brain` 目前只支持纯文本：`openai-types.ts` 把 `messages[].content` 硬类型钉死为
`string`，`http.ts` 遇到非字符串走 `JSON.stringify`，`deepseek-web.ts` 唯一出口是
`cdp.send('Input.insertText')`。结果是 **OpenCode 侧任何带图请求进来，图片会退化成一段
base64 垃圾文本**，模型根本看不到图。

sir 2026-10-24 要求开工「大脑图片支持」。

### 已实证的前置事实（本轮真机探测，非推断）

2026-10-24 用 puppeteer 连 `http://127.0.0.1:9222` 在新标签页探测 `chat.deepseek.com`：

| 判据 | 实测结果 |
|---|---|
| `input[type=file]` 存在 | ✅ 唯一一个，`accept` 含 `.png,.jpg,.jpeg,.svg,.webp,.gif,.bmp,.pdf`，`multiple=true`，`display:none` |
| `uploadFile()` 是否被前端接受 | ✅ `input.files` 由 1 → 0（被前端消费） |
| 前端是否渲染附件预览 | ✅ 输入区新增 `img`，`src=blob:https://chat.deepseek.com/...`，class `_9f130b7` |
| DOM 增量 | 14848 → 16741 字符（+1893 = 预览卡片） |
| 稳定时间 | 500ms 内完成，其后 5s 采样无变化 |

**结论：隐藏 input 可被 `uploadFile()` 驱动，且「输入区出现 `img[src^="blob:"]`」是干净的
上传完成信号**，不需要 hack 式定时等待。

### 调研结论（有来源，非主张）

1. **OpenAI 多模态 content 存在三种方言**。`BerriAI/litellm`
   `litellm/litellm_core_utils/prompt_templates/common_utils.py:203`：
   `_IMAGE_CONTENT_PART_TYPES = frozenset({"image_url", "input_image", "image"})`
   —— 分别是 Chat Completions / Responses API / Anthropic 风格。
   同文件 `:246` 的 `_image_content_url` 还显示 **`image_url` 既可能是字符串也可能是对象**：
   ```python
   if part_type == "image_url":
       image_url = part.get("image_url")
       if isinstance(image_url, str): return image_url
       return image_url.get("url") if isinstance(image_url, Mapping) else None
   ```
   `image_url.detail` 字段真实存在（`litellm/llms/vertex_ai/gemini/transformation.py:160`）。
   data URI 形态 `data:image/<subtype>;base64,<data>`
   （`litellm/litellm_core_utils/prompt_templates/factory.py:166` `convert_to_ollama_image`）。

2. **puppeteer `uploadFile()` 有硬约束**。官方文档 pptr.dev 25.16.0：
   > "For locals script connecting to remote chrome environments, **paths must be absolute**."

   `deepseek-brain` 正是 `browserURL: http://127.0.0.1:9222` 连既有 Chrome —— **落盘临时文件
   必须是绝对路径**，否则传不进去。另：文档明确 "will not validate whether the file paths
   exists"，即文件不存在时静默失败，本卡必须自己前置校验。

3. **`chat.deepseek.com` 附件数量/大小上限：未找到权威来源**。不编造数值。改为把「多图一次
   上传能否成功」列为实测验收项（A9），测出下限后回写 README。

### 本卡边界

**只做「当前轮 user 消息的图片」**（sir 2026-10-24 拍板）。历史轮次的图片不重传 —— DeepSeek
网页会话自身已持有那些附件，重传只会反复堆叠并撞上未知的上限。

## Deliverables

### A. 类型层：接受多模态 content

`src/server/openai-types.ts` 新增：

```ts
export type OpenAIContentPart =
  | { type: 'text'; text: string }
  | { type: 'image_url'; image_url: string | { url: string; detail?: string } }
  | { type: 'input_image'; image_url: string | { url: string } }   // Responses API 方言
  | { type: 'image'; source?: { type: 'base64'; media_type: string; data: string } }  // Anthropic 方言

export interface OpenAIChatRequest {
  messages: Array<{
    role: string
    content: string | OpenAIContentPart[]      // ← 从 string 放宽
    tool_call_id?: string
    tool_calls?: unknown[]
  }>
  // ...其余不变
}
```

`src/types.ts` 的 `OpenAIMessage` 增加可选 `images?: string[]`（**绝对路径**）。

### B. 入口层：data URI → 绝对路径临时文件

`src/server/http.ts` 的 `toInternal()` 拆成两步：

1. `content` 为数组时：`text` 段按原顺序拼接为 `content` 字符串；图片段抽取并解码。
2. 解码支持 `data:` URI（`data:image/<subtype>;base64,<data>`）；`http(s)` 远程 URL 本卡
   **不支持**（明确报错，见 C 段错误语义），避免把 SSRF 面开进 shim。
3. base64 → 写文件到 `os.tmpdir()/deepseek-brain-uploads/<随机目录>/<n>.<ext>`，
   **返回绝对路径**。
4. 本轮结束（无论成功/失败）删除该临时目录 —— 用 `try/finally` 保证。

不写成 `Buffer.from(b64)` 直接丢给 transport：transport 只认路径（puppeteer 约束），且 base64
串进 prompt 会撑爆网页版上下文。

### C. 规划层：只取当前轮图片 + 失败语义

`src/core/planner.ts`：

- `GenerateRequest`（`src/core/types.ts`）增加 `images?: string[]`。
- 新增内部函数 `currentTurnImages(delta)`：取 `delta` 中**最后一条 `user` 消息**的 `images`。
  返回 `string[]`（可能为空）。
- 传给 `transport.generate({ prompt, thinking, timeoutMs, images })`。
- **compaction 路径不受影响**：`buildCompactPrompt` 那一路不带 images（摘要不需要图）。

**错误语义（重要）**：上传失败时**必须抛错**，绝不允许「静默降级成纯文本发送」—— 那会让模型
在没有图的情况下作答，产出看似正常实则错位的回答，比直接报错危险得多。统一错误前缀
`upload_failed:`，与既有 `no_request_after_send:` / `ui_changed:` 风格一致。

`src/server/http.ts` 把新增错误映射为 HTTP 400（客户端错误：给了不支持的 URL 形态）或
502（上游/浏览器失败），并在 `error.message` 保留前缀便于定位。

### D. 传输层：上传 → 等完成 → 再发送

`src/transports/deepseek-web.ts` 的 `generate()`，在现有 `insertText` 之前插入：

```ts
if (req.images?.length) {
  for (const p of req.images) if (!isAbsolute(p)) throw new Error(`upload_failed: 路径必须绝对`)
  const input = await page.$(sel.fileInput)
  if (!input) { await dumpDom('no-file-input'); throw new Error('upload_failed: 未找到 file input') }
  const before = await countImagePreviews(page, sel.imagePreview)
  await input.uploadFile(...req.images)                    // 绝对值展开，一次传多张
  await waitForImagePreviews(page, sel.imagePreview, before + req.images.length, timeout)
}
// 原有 insertText + clickSend 不变
```

- `waitForImagePreviews` 用 `page.waitForFunction` 等 `img[src^="blob:"]` 计数达标
  （实测 500ms 内完成），超时抛 `upload_failed: 上传未完成`。
- 上传在 `insertText` **之前**，保证发送时附件已就位。
- 沿用既有 `generating` 单飞锁，避免并发上传互相踩。

## Review questions

1. **`upload_failed:` 用 400 还是 502？** 我的倾向：data URI 形态非法 → 400（客户端错），
   浏览器/上传超时 → 502（上游错）。但 `http.ts` 现有 catch 是**统一 502**。是否要为这个区分
   改造错误分类，还是保持「一律 502 + message 前缀区分」的现状更稳？
2. **临时文件放 `os.tmpdir()` 是否可接受？** 备选是放项目内 `.uploads/`（好排查、要加 gitignore）。
   我选 `os.tmpdir()` 是为了不污染工作树（A11），代价是错误现场不好事后取证。请裁决。
3. **`image` 方言（Anthropic 风格）是否该进 v1？** 我加了，理由是 LiteLLM 明确把三者并列；
   但 OpenCode 实际只会发 `image_url`。多支持一种方言 = 多一份必须维护的测试面。是否应砍掉
   只留 `image_url` + `input_image`？
4. **多图上限未知**：A9 若测出「第 3 张起失败」，是应该在 shim 侧硬性截断并告警，还是原样透传
   给上游报错？我倾向**原样透传**（诚实暴露上游限制，不在 shim 里编造规则）。
5. **`detail` 字段**：解析出来但 DeepSeek 网页版无法表达「低分辨率/高分辨率」语义。是静默忽略
   （当前做法），还是记一条 debug 日志？
