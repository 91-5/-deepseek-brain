### 重点审查 1：失败语义不可静默降级（Constraint 3）

`deepseek-web.ts` `generate()` 的 `if (req.images && req.images.length > 0) { await uploadImages(req.images, sel) }` 位于 `cdp.send('Input.insertText', ...)` 与 `clickSend(sel.send)` **之前**，且 `uploadImages` 内部 5 条失败路径全部 `throw new Error('upload_failed: ...')`：

| 路径 | 位置 | 结果 |
|---|---|---|
| bridge 未启动 | `uploadImages` 首行 | 抛 `upload_failed: bridge not started`，`insertText`/`clickSend` 零调用 |
| 附件路径非绝对 | 前置校验 for 循环 | 抛 `upload_failed: 附件路径必须绝对`，`uploadFile` 零调用（A7 单测断言） |
| 附件文件不存在 | 前置校验 for 循环 | 抛 `upload_failed: 附件不存在`，`uploadFile` 零调用（A8 单测断言） |
| `page.$(sel.fileInput)` 为 null / tagName≠input | 上传前 | `dumpDom('no-file-input')`/`dumpDom('file-input-not-input')` 后抛 `upload_failed`，`uploadFile` 零调用 |
| `input.uploadFile` 抛错 | try/catch | 抛 `upload_failed: uploadFile 调用失败`，`waitForFunction` 不执行 |
| `waitForFunction` 15s 超时 | try/catch | `dumpDom('upload-timeout')` 后抛 `upload_failed: ... 未观察到附件预览`，`insertText` 永不执行 |

`uploadImages` 抛错沿 `generate()` 的 async generator 向上传播，调用方（planner/http）拿到的是 `upload_failed:` 错误而非已发出的纯文本答案 —— **没有任何一条路径会落到 `insertText` 之后仍继续**。A8 桩测试「uploadFile 抛错时 `cdp.Input.insertText` 与 `click` 均零调用」是这条不变量的机器守护。✅

### 重点审查 2：临时文件清理三条路径（Constraint 2）

临时文件由 `http.ts` 的 `toInternal()` 产生，清理函数 `cleanup`（= `runCleanups`，幂等）挂在 `InternalRequest` 上，`http.ts` 主请求处理是 **`try {...} catch {...} finally { cleanup() }`** 三行结构：

- **`uploadImages` 自身抛错**：`runAgentTurn` → `transport.generate` 消费循环里 `for await` 收到 `upload_failed` 错误 → 沿 planner 逐层传播 → 落到 `http.ts` 的 `catch`（502）→ `finally { cleanup() }` 执行。✅
- **`insertText` 抛错**（如 CDP session 失效）：同理，`catch` 502 → `finally` 清理。✅
- **`clickSend` 超时**（`timeout: generation exceeded limit` 于 `generate()` 末尾 throw）：同理。✅

`toInternal()` 自身内部另有第二层防护：`catch (e) { runCleanups(); throw e }` —— 若**第 N 条消息** `prepareContent` 在落盘中途失败（`mkdirSync`/`writeFileSync` 抛错），前面第 1..N-1 条消息已 push 进 `cleanups` 的临时目录会被清理后再抛出，不留孤儿目录。这层是必要的，因为 `http.ts` 的 `finally` 只在 `toInternal` **成功返回**之后才绑定 `cleanup = internal.cleanup`；`toInternal` 失败时 `cleanup` 仍是初始的 no-op `() => {}`，第二层 `runCleanups()` 是唯一清到前面已写临时文件的路径。两层各自覆盖「成功/失败」互斥的场景，无重叠、无遗漏。✅

`generate()` 本身的 `finally { generating = false; entryIndex = -1 }` 只重置单飞锁状态，与临时文件无关（临时文件生命周期在 http 层，不在 transport 层），这条分层正确。✅
